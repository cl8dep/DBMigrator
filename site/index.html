Why db-migrator

Migrate. Validate.
Sanitize.

Validate first

Connects to source DB before anything moves. Catches missing tables, wrong column types, NOT NULL violations. Zero surprises mid-migration.

All-or-nothing

Sanitization runs inside a single transaction. One rule fails → full rollback. No partial states, no half-redacted tables.

Parallel for speed

Set parallel_jobs: 4 to use multiple workers. Auto-switches to directory format. Cut migration time significantly.

Live progress

Spinner streams pg_dump verbose output in real time. Elapsed time per step. You always know exactly what's happening.

Pre-flight checks

Detects idle in transaction connections that would block pg_dump — before the dump even starts.

Sanitization

There's a strategy
for that.

Five built-in strategies cover every data sanitization scenario. Declare them per column in YAML.

static

Fixed value for every row. For hashed passwords, redacted fields.

strategy: static
value: "REDACTED"

null_value

Sets the column to NULL. Column must be nullable — validated before execution.

strategy: null_value

template

{column} refs resolved per row via SQL. Unique, traceable values.

strategy: template
value: "user_{id}
@redacted.local"

faker

Realistic fake data via Bogus. 25+ methods: names, emails, phones, IBANs.

strategy: faker
faker: email

hash

SHA-256 of original value. Deterministic — preserves FK relationships.

strategy: hash

Configuration

Declare it.
Run it.

One YAML file. Which tables, which columns, which strategy. Passwords via environment variables. The tool handles the rest.

  • ${ENV_VAR} interpolation — passwords never live in the config file
  • Optional where clause to skip admin rows or seed data
  • Mix strategies freely per column — no constraints
  • parallel_jobs: N for faster dump/restore on large databases
config.yaml 
sanitize:
  - table: users
    where: "role != 'admin'"
    columns:
      - name: email
        strategy: template
        value: "user_{id}@redacted.local"

      - name: first_name
        strategy: faker
        faker: first_name

      - name: password_hash
        strategy: static
        value: "$2b$10$REDACTED"

      - name: national_id
        strategy: hash

      - name: avatar_url
        strategy: null_value

Process

Three steps.
One command.

01

Validate

Connects to source DB. Checks tables, columns, nullability, and strategy config. Reports every error before any data moves.

02

Migrate

pg_dump on source, pg_restore on target. Parallel workers, SSL modes, table exclusions — all configured in YAML.

03

Sanitize

All rules in one transaction on the target. Full rollback on any error. Target database is production-safe when done.

Get started

Up and running
in seconds.

# Download latest binary (macOS arm64)
curl -L https://github.com/cl8dep/DBMigrator/releases/latest/download/db-migrator-macos-arm64 \
  -o db-migrator && chmod +x db-migrator

# Copy and edit config
cp config.example.yaml config.yaml

# Validate against source DB
SOURCE_DB_PASSWORD=... TARGET_DB_PASSWORD=... \
  ./db-migrator validate --config config.yaml

# Run full pipeline
SOURCE_DB_PASSWORD=... TARGET_DB_PASSWORD=... \
  ./db-migrator run --config config.yaml
docker build -t db-migrator .

docker run --rm \
  -e SOURCE_DB_PASSWORD=... \
  -e TARGET_DB_PASSWORD=... \
  -v $(pwd)/config.yaml:/app/config.yaml:ro \
  db-migrator run --config /app/config.yaml
gcloud run jobs create db-migrator \
  --image gcr.io/my-project/db-migrator:latest \
  --set-secrets SOURCE_DB_PASSWORD=source-db-pass:latest \
  --set-secrets TARGET_DB_PASSWORD=target-db-pass:latest \
  --args="run,--config,/secrets/config.yaml"

# Execute the job
gcloud run jobs execute db-migrator
